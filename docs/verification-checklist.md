# 検証チェックリスト

手順書を公開する前に、**書いた本人が自分で潰すための一覧**です。

一度きりの点検表ではなく、**次の文書にも使える形**にしています。
[STEP 4 改訂案](./step4-email-proposal.md) への適用結果を、後半に記載しています。

## なぜチェックリストで確認するか

手順書の誤りは、書いているときには見えにくいものです。
書き手は前提を既に知っているため、**抜けた前提に気づけません。**

筆者は、止められないサーバー運用の現場で、**手順書を読む側**を経験しました。
曖昧な一文や抜けた前提が、そのまま作業の停止につながる場面があります。
その経験から、**書き手の記憶ではなく、決まった項目で確認する**ようにしています。

## A. 読者と目的

- [ ] 対象読者が**一種類**に決まっているか（複数の読者を一枚に混ぜていないか）
- [ ] 読者が達成したいことが、冒頭に書かれているか
- [ ] 読者が**この文書に来る前に済ませていること**が明示されているか
- [ ] 対象外の読者・対象外の構成が明示されているか

## A-2. 読む理由 ★報告書・記録の場合

**Aとは点検する対象が違うため、別立てにしています。**

手順書には、**用事のある読者**が来ます（「メールを使いたい」）。
報告書・記録には、**用事のない読者**が来ます。読むかどうかを、冒頭でその場で決める人です。

だから、渡すものが違います。
手順書に要るのは「**これを読むと何ができるか**」、
記録に要るのは「**なぜあなたがこれを読むのか**」です。

- [ ] 冒頭の3〜5行だけで、読み手が**「自分はこれを読むべきか」を判断できる**か
- [ ] 書いてあるのが「**何について**」ではなく「**なぜ読むか**」になっているか
- [ ] 想定する読み手を一人思い浮かべ、
      **冒頭を読んだ直後にその人が何を思うか**を、言葉にできるか
- [ ] 読み手が**身構える**書き出しになっていないか
- [ ] 書き手の立場（どちら側の人間か）が、早い段階で分かるか

> **「ふーん」しか出てこなければ、冒頭が仕事をしていません。**

※この項目は、**本記録自身のREADMEを書き直す過程で必要と分かった**ものです。
当初のREADMEは「何が書いてあるか」だけを述べており、
読み手が身構えたまま本文に入る構成になっていました。

## B. 前提条件

- [ ] 前提条件が、手順より**前**に書かれているか
- [ ] 手順の途中で初めて必要になる情報がないか
- [ ] 必要なものの**入手先・確認方法**が書かれているか
- [ ] 契約プラン・OS・バージョンの範囲が明示されているか

## C. 経路の分岐

- [ ] 読者の状況で手順が変わる場合、**分岐が冒頭にあるか**
- [ ] 分岐の軸が、**提供側の管理単位ではなく読者の目的**になっているか
- [ ] どちらを選べばよいか迷う読者への**推奨**が書かれているか
- [ ] 分岐が排他か併用可かが分かるか

## D. 手順

- [ ] 一つの手順に複数の操作を詰め込んでいないか
- [ ] 操作（何をするか）と説明（なぜそうするか）が分かれているか
- [ ] UIのラベル、コマンド、入力値、出力が**区別できる書式**になっているか
- [ ] 手順が実行順に並んでいるか
- [ ] 例外・トラブル対応が、通常手順から分かれているか

## E. 設定値・参照情報

- [ ] 設定中に参照し続ける情報が、**一箇所にまとまっているか**
- [ ] 値の**出典**（公式ページ・確認日）が記載されているか
- [ ] 間違えやすい値に、注意が添えられているか
- [ ] 複数ページを往復しないと設定できない状態になっていないか

## F. 成功の判定

- [ ] **何ができたら完了か**が明示されているか
- [ ] 判定が、読者自身の操作で確認できるか
- [ ] 一部だけ成功した場合の**切り分け**が示されているか

## G. 失敗したとき

- [ ] 失敗時に戻れる場所が示されているか
- [ ] 症状別に参照先が分かれているか
- [ ] **失敗が目に見えない**種類の事象に、注意があるか

## H. 用語

- [ ] 専門用語に説明があるか、説明ページへの導線があるか
- [ ] 同じものを指す語が、文書内で統一されているか
- [ ] 公式の画面表記と、文書内の表記が一致しているか

## I. 事実の区分 ★この記録群の中核

- [ ] **事実・分析・提案・未確認**が区別されているか
- [ ] 実施していないことを、実施したと書いていないか
- [ ] 確認していない値・画面を、確認したように書いていないか
- [ ] 公式文書を「誤り」と断定していないか
- [ ] 外から見えない理由がある可能性に触れているか
- [ ] 推測で書いて誤った箇所を、**訂正の経緯ごと**残しているか
- [ ] **本文で主張している数を、自分で数え直したか**（見出しの数字を含む）
- [ ] 表や一覧の件数と、本文中の記述が一致しているか
- [ ] **他の記録・節・文書を番号や見出しで参照している箇所は、
      実際にその参照先を開いて、内容が一致することを確かめたか**

## J. 出典とリンク

- [ ] 参照した公式ページのURLと**確認日**が記載されているか
- [ ] リンクが現在も有効か（**実際に開いて確認したか**）
- [ ] 開いて確認したリンクと、転記しただけのリンクを区別しているか
- [ ] 公式文書を大量転載していないか
- [ ] 引用に出典が併記され、短い範囲に留まっているか
- [ ] ロゴ・公式画面の画像を無断使用していないか

## K. 秘密情報

- [ ] 会員ID、サービスコード、契約情報が含まれていないか
- [ ] ドメイン名、メールアドレス、IPアドレスが含まれていないか
- [ ] パスワード、秘密鍵、トークンが含まれていないか
- [ ] 現職および取引先を特定できる情報が含まれていないか
- [ ] コマンドの実行例やスクリーンショットに、上記が写り込んでいないか

## L. 立場の明示

- [ ] 非公式の文書であることが明示されているか
- [ ] 依頼・許可を受けたものではないと明示されているか
- [ ] 「公式」「監修」「採用された改善案」と誤認させる表現がないか

## M. 第三者による読解（実施できた場合のみ）

- [ ] 技術に詳しくない一人に読んでもらったか
- [ ] 支援なしでどこまで到達できたかを記録したか
- [ ] どの語・どの手順で止まったかを記録したか

> **実施していない場合、「テスト済み」とは書かない。**
> 実施しなかったこと自体を、限界として記載する。

**必要な環境：ブラウザと、メールソフト1つ。**
**Windows は不要です。**理由は下記「この検証で確かめないこと」に記載します。

所要はおよそ1時間と見積もった。**上から順に行う。**1が他のすべての前提である。

| # | やること | 使うもの | 控えるもの |
|---|---|---|---|
| **1** | コントロールパネルでメールアドレスを1件作る | ブラウザ | **画面名・メニュー名・項目名**（他の全項目の前提） |
| **2** | ウェブメールにログインし、自分宛に送って受信する | ブラウザ | **ログインURL**と手順 |
| **3** | メールソフトから接続する（IMAP / SSL・TLS / 受信993 / 送信587） | メールソフト | ソフト名と**バージョン**、接続の可否 |
| **4** | サーバー名に**独自ドメイン**を入れて試す | 同上 | 接続できるか（**できない前提で書いている**） |
| **5** | 送信ポートを **465** に変えて試す | 同上 | 両方通るか、条件があるか |
| **6** | IMAPパスプレフィックス `INBOX` の要否を確認する | 同上 | 指定が必要だったか |
| **7** | STEP 4 本文を通読し、ウェブメールへの言及の有無を再確認する | ブラウザ | 有無 |

**確かめているのは設定値です。**
サーバー名・SMTP認証・ユーザー名の形式は、**メールソフトが何であっても同じ**です。

**［追記］**ただし実測では、**ソフトによって既定で選ぶポートと暗号化方式が違いました。**

| ソフト | 既定で選んだ受信 | 既定で選んだ送信 |
|---|---|---|
| macOS「メール」 | 143（TLS有効） | 587 |
| Thunderbird | 993 / SSL・TLS | 465 / SSL・TLS |

**したがって「1つのソフトで接続できれば値の正しさが示せる」とは言えません。**
サーバー名やユーザー名の形式は共通ですが、
**ポートと暗号化方式は組み合わせで決まり、ソフトの既定も一致しません。**
本検証では**2つのソフト**で確認しました。
